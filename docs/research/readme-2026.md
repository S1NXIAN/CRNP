# README.md standards and best practices — 2026 research digest

All URLs accessed 2026-09-22. Canonical older sources are cited with their original dates.
Inline citation format: source (author, publication date), URL (accessed 2026-09-22).
Source tiers: **first-party** = the org that owns the claim (GitHub Docs/Blog, Diátaxis, Google, Microsoft, NN/g, AGENTS.md, llms.txt.org, .NET Foundation); **secondary** = community/blog opinion, labeled as such.

## 1. Question & problem

A long "living plan" README (project plan, debate notes, roadmap, changelog, nested sub-sections) fails both audiences it now serves: humans who scan for "what is this / how do I run it" and coding agents that need build/test/convention context without prose noise.
This digest verifies 2026 README standards against primary sources and produces a reorganization checklist: what a README must keep, what moves to linked docs, and how agent-facing files (AGENTS.md, copilot-instructions, llms.txt) coexist with the human README.

## 2. Findings

### 2.1 Canonical structure (and what counts as bloat)

- **GitHub's authoritative topic list (the floor, not an order):** a README "typically include[s] information on" — what the project does, why it's useful, how to get started, where to get help, who maintains/contributes.
— GitHub Docs, *About the repository README file*, https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes (accessed 2026-09-22).
- **README is one of a set, not a dump:** "A README, along with a repository license, citation file, contribution guidelines, and a code of conduct, communicates expectations for your project" — i.e. license/CoC/contributing are *separate files* the README links to, GitHub's community-profile checklist checks for README, CODE_OF_CONDUCT, LICENSE, CONTRIBUTING (plus security policy and issue templates).
— GitHub Docs, *About the repository README file* (same URL); GitHub Docs, *About community profiles for public repositories*, https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories (accessed 2026-09-22).
- **Hard scope rule:** "A README should only contain information necessary for developers to get started using and contributing to your project. Longer documentation is best suited for wikis." (GitHub's README doc points long-form out of the README entirely.)
— GitHub Docs, *About the repository README file*, same URL (accessed 2026-09-22).
- **Microsoft-adjacent canonical section list (.NET Foundation "Crafting a good README", undated [date UNVERIFIED]):** one-paragraph summary; project status (shipping/experimental/orphaned); current CI build status as a red/green badge linking to public build results; problem it solves and why use it; install & use; related projects and how yours differs; link to contribute file; developer getting-started/community channels; feedback routes; license type + link to LICENSE; high-level roadmap *or link to* roadmap docs/open issues. "If you have lots of information for a particular topic then it is good to split that out into a separate file in your /Documentation folder with a link in the README."
— .NET Foundation, *Crafting a good README*, https://github.com/dotnet-foundation/foundation/blob/master/guidance/readme-guide.md (accessed 2026-09-22).
- **GitHub's own docs-writing guidance (applies to repo docs):** keep it clear (plain language), concise ("Document only necessary information… if you find yourself including information that isn't strictly necessary, move it into separate, smaller documents and link to them"), structured (most important first; headings + a table of contents; bold/lists to aid scanning; **"Aim for 10% or less text highlighting"**); it explicitly recommends the **Diátaxis** framework for repo docs organization and links an example `docs/` structure.
— GitHub Blog, Ellich & Browning, *Documentation done right: A developer's guide* (2025-05-14), https://github.blog/developer-skills/documentation-done-right-a-developers-guide/ (accessed 2026-09-22).
- **Diátaxis taxonomy (what repo docs get sorted into):** four and only four forms — tutorials (learning), how-to guides (goals), reference (information), explanation (understanding); each document should fit one category.
— Diátaxis, *Foundations*, https://diataxis.fr/foundations/ (accessed 2026-09-22); endorsed for repos by GitHub Blog (same URL as above).
- **Vision/roadmap placement:** "Add them to your README, or create a separate file called VISION… if there are other artifacts that could help, like a project roadmap, make those public as well"; also: keep documentation current — "delete your outdated documentation or indicate it is outdated."
— GitHub, *Open Source Guide — Best Practices for Maintainers*, https://opensource.guide/best-practices/ (accessed 2026-09-22).
- **2026 secondary consensus on order (not first-party):** one-line description → context paragraph → visual → install → usage → configuration → contributing → license; "A strong README follows a predictable shape because predictability is what makes it scannable"; length guidance ~100–300 lines for most libraries, then move reference material to `docs/`.
— Pushpen blog (2026-06-25), https://pushpen.dev/blog/how-to-write-a-good-github-readme (accessed 2026-09-22) [secondary].
- **Obsolete bloat (community canon, secondary):** repeated title/H1 (the repo URL already shows it); changelog ("rely on the releases tab"); full license text (GitHub auto-detects LICENSE — "don't say anything in the README about the license, it's just pure noise"); contributor lists (there's a Contributors tab; use an Acknowledgements section only to credit people); API docs wholesale ("The README is not user documentation for everything you have in your repo"); ≤5 badges per line, same height per line; `##` for sections, avoid `###`, `####` "absolutely prohibited".
— Yegor Tsyumentsev, *Elegant READMEs* (2019-04-22), https://www.yegor256.com/2019/04/23/elegant-readme.html (accessed 2026-09-22) [secondary].
- **Shortest-form canon (secondary):** "The ideal README is as short as it can be without being any shorter. Detailed documentation is good — make separate pages for it! — but keep your README succinct."
— *art-of-readme* (2016-10-01), https://github.com/hackergrrl/art-of-readme (accessed 2026-09-22) [secondary].
- **Physical ceiling:** GitHub truncates rendered README content beyond **500 KiB**; README recognized only in `.github/`, root, or `docs/` (priority order `.github` > root > `docs`).
— GitHub Docs, *About the repository README file*, same URL (accessed 2026-09-22).

### 2.2 Navigation aids (TOC, anchors, tables vs lists)

- **GitHub auto-generates the TOC:** "When you use two or more headings, GitHub automatically generates a table of contents" accessible via the Outline icon in the rendered file header; same auto-TOC exists for every rendered Markdown file, README included.
— GitHub Docs, *Basic writing and formatting syntax* (Headings), https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax (accessed 2026-09-22); GitHub Docs, *About the repository README file*, same URL as above (accessed 2026-09-22).
- **Anchor algorithm (for stable in-doc links):** lowercase; spaces → hyphens; other whitespace/punctuation removed; markup stripped; duplicate headings get `-1`, `-2` suffixes. **Editing a heading or reordering identical headings changes anchors — all links to them must be updated.** Custom `<a name="…">` anchors work but are *not* included in the outline/TOC.
— GitHub Docs, *Basic writing and formatting syntax* (Section links, Custom anchors), same URL (accessed 2026-09-22).
- **When a hand TOC earns its place:** first-party guidance *prescribes* in-doc navigation for long content — "In a longer document… include a table of contents with links to subheadings. Add *Back to top* links at the end of sections"; GitHub's docs blog likewise: "Use headings and a table of contents to tell your readers where to find specific information."
— Microsoft Style Guide, *Scannable content*, https://learn.microsoft.com/en-us/style-guide/scannable-content (accessed 2026-09-22); GitHub Blog, *Documentation done right*, same URL as above (accessed 2026-09-22).
- **…and argues against a manual duplicate:** "a hand-written list is duplicated work that goes stale within two releases" — GitHub's built-in Outline covers it; keep one only if the file is genuinely long.
— Omniwebkit (2026-08-08), https://omniwebkit.com/blog/how-to-write-a-good-readme (accessed 2026-09-22) [secondary]. **Synthesis:** rely on the Outline for ≤~1 screen-plus files; a manual TOC only for very long READMEs, and if written, keep it to `##` depth.
- **Link hygiene:** use relative links for in-repo files/images (works across branches and in clones; absolute links may break); link text must be on a single line (a line-broken link fails).
— GitHub Docs, *Basic writing and formatting syntax* (Relative links), same URL (accessed 2026-09-22); GitHub Docs, *About the repository README file*, same URL as above (accessed 2026-09-22).
- **Tables vs lists:** first-party framing is "organize information" tables (GitHub) vs. scannable lists (Microsoft): lists should have "at least two items but (if possible) no more than seven", items short enough that "the reader should see at least two, and preferably three, list items at a glance", structure parallel across items; a **term list** (bold term + definition) is the sanctioned lighter alternative to a table; numbered lists only for sequence/priority.
— GitHub Docs, *Organizing information with tables*, https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-tables (accessed 2026-09-22); Microsoft Style Guide, *Lists* (2026-02-10), https://learn.microsoft.com/en-us/style-guide/scannable-content/lists (accessed 2026-09-22).
- **Feature matrices:** tables are a named scanning device in both house styles ("Headings, Lists, Pull quotes, Sidebars, Tables"); 2026 secondary guidance picks tables for option/flag matrices ("option name, type, default, description… Tables are scannable; prose is not") and lists for short feature bullets.
— Microsoft Style Guide, *Scannable content*, same URL (accessed 2026-09-22); OpenMark (2026-02-19), https://openmarkapp.com/blog/how-to-write-readme-md (accessed 2026-09-22) [secondary].

### 2.3 Scannability rules (headings, wrapping, folding, images, badges)

- **Headings:** one `#` H1 per page, never skip levels, no empty headings; **sentence case for all headings**; task headings start with a bare infinitive ("Create an instance"), concept headings are noun phrases; avoid leading `-ing`; don't number sections ("rely on heading hierarchy and order"); don't put links or bare code items in headings; keep punctuation simple.
— Google, *Developer documentation style guide — Headings and titles* (updated 2026-06-08), https://developers.google.com/style/headings (accessed 2026-09-22).
- **Headings are the reading interface:** "If readers don't read the headings, they probably won't read the text that follows, either"; keep headings short and "put the most important idea at the beginning"; sentence-style capitalization; don't stack two headings with no text between; "One heading level is usually plenty for a page or two of content."
— Microsoft Style Guide, *Headings*, https://learn.microsoft.com/en-us/style-guide/scannable-content/headings (accessed 2026-09-22).
- **Heading depth convention (first-party MicrosoftDocs house style):** increment by one, don't skip levels, one H1, "Limit depth to H3 or H4", no markup inside headings.
— MicrosoftDocs/PowerShell-Docs, *General Markdown guidance*, https://github.com/MicrosoftDocs/PowerShell-Docs/blob/main/reference/docs-conceptual/community/contributing/general-markdown.md (accessed 2026-09-22) [first-party house style, not the public Style Guide].
- **Heading hierarchy is an accessibility contract:** "It's important not to skip heading levels (for example, `##` followed by `####`)" — assistive tech navigates by them, and correct hierarchy "also helps visual users scan content more easily"; newspaper model: largest at top.
— GitHub Blog, Streater, *5 tips for making your GitHub profile page accessible* (2023-10-26), https://github.blog/2023-10-26-5-tips-for-making-your-github-profile-page-accessible/ (accessed 2026-09-22).
- **Line wrapping:** in `.md` files soft line breaks render as one line (needs two trailing spaces / `\` / `<br/>`), so *source* wrapping is a readability-of-source choice; for *rendered* text, NN/g prescribes "short text lines (around 50–75 characters)" plus short paragraphs separated by white space as the core chunking moves.
— GitHub Docs, *Basic writing and formatting syntax* (Line breaks), same URL (accessed 2026-09-22); NN/g, Moran, *How Chunking Helps Content Processing* (2016-03-20), https://www.nngroup.com/articles/chunking/ (accessed 2026-09-22).
- **Folding `<details>`:** GitHub's first-party use case is "technical details… that may not be relevant or interesting to every reader"; any Markdown (headers, images, code) collapses; `<summary>` labels the toggle; `<details open>` starts expanded. GitHub's a11y guidance adds: put *long image descriptions* in a `<details>` tag or link out.
— GitHub Docs, *Organizing information with collapsed sections*, https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections (accessed 2026-09-22); GitHub Blog, *5 tips… accessible*, same URL (accessed 2026-09-22). **Synthesis:** fold secondary detail only — the quickstart/usage/license core must stay visible.
- **Alerts/callouts are rationed:** "Use alerts only when they are crucial for user success and limit them to one or two per article… avoid placing alerts consecutively."
— GitHub Docs, *Basic writing and formatting syntax* (Alerts), same URL (accessed 2026-09-22).
- **Images/screenshots (Google house rules):** use images only when words can't do it; **don't use images of text, code, or terminal output — use actual text** (paste output as a code block); crop screenshots to the relevant region, keep one OS per doc set, no PII (100%-opacity overlay if unavoidable), SVG preferred for diagrams (PNG fallback), MP4 over animated GIF; alt text ≤155 chars, descriptive, no "image of…"; introduce each image with a complete sentence.
— Google style guide, *Diagrams, figures, and other images* (updated 2025-05-16), https://developers.google.com/style/images (accessed 2026-09-22).
- **Alt text + links + lists (README-specific a11y):** "Think of alt text like a tweet: be succinct, concise and descriptive"; include "screenshot of…" context; descriptive link text (never "here"/"click here"); real list markup only — emoji as bullet characters break screen-reader list semantics; emoji in quantity is called out as distracting/jarring.
— GitHub Blog, *5 tips… accessible*, same URL (accessed 2026-09-22).
- **Badges — first-party mechanics:** status badges are meant for the README ("A common place to add a status badge is in the `README.md` file"); URL form `…/actions/workflows/WORKFLOW-FILE/badge.svg` with `branch`/`event` params; private-repo badges aren't externally accessible.
— GitHub Docs, *Adding a workflow status badge*, https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/monitoring-workflows/adding-a-workflow-status-badge (accessed 2026-09-22).
- **Badges — what they're for:** CI build status as red/green badge *linking to publicly accessible build results*, plus project status — a live maintenance signal, not decoration.
— .NET Foundation, *Crafting a good README*, same URL as above (accessed 2026-09-22).
- **Badge abuse (community canon):** "Be judicious in your use of badges. They're easy to abuse… They add visual noise to your README and generally only function if the user is reading your Markdown in a browser online" — ask of each badge "what real value is this providing to the typical viewer".
— *art-of-readme*, same URL (accessed 2026-09-22) [secondary]. 2026 secondary caps it at "3–4 meaningful ones. A row of 12 badges is noise" — OpenMark, same URL [secondary].
- **Why all of this works (measured):** concise text scored **+58%** usability, scannable layout **+47%**, combined **+124%** vs promotional control; 79% of users always scan, 16% read word-for-word.
— NN/g, Nielsen, *How Users Read on the Web* (1997-10-01), https://www.nngroup.com/articles/how-users-read-on-the-web/ (accessed 2026-09-22).
- **Reading budget:** users read at most ~28% of words on an average page, more realistically ~20%; only 4.4 extra seconds per +100 words; first 3 paragraphs get 81/71/63% look rates, the 4th drops to 32%.
— NN/g, Nielsen, *How Little Do Users Read?* (2008-05-05), https://www.nngroup.com/articles/how-little-do-users-read/ (accessed 2026-09-22); NN/g, Nielsen, *Website Reading: It (Sometimes) Does Happen* (2013-06-24), https://www.nngroup.com/articles/website-reading/ (accessed 2026-09-22).
- **F-pattern rules (unbroken text):** first two paragraphs must state the most important information; start subheads/paragraphs/bullets with information-carrying words (readers catch the first ~2 words, not the third); "Good web formatting reduces the impact of F-scanning. If your pages have big chunks of unformatted text, people will scan it in an F-shape."
— NN/g, Nielsen, *F-Shaped Pattern For Reading Web Content* (2006-04-16), https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content-discovered/ (accessed 2026-09-22); NN/g, Pernice, *F-Shaped Pattern of Reading: Misunderstood, But Still Relevant* (2017-11-12), https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/ (accessed 2026-09-22).
- **Layer-cake is the pattern to design for:** fixations mostly on headings/subheadings, then reading the body under the interesting one — "by far the most effective way to scan pages", but only if headings are (1) easy to identify (contrast, spacing) and (2) accurate summaries of their section; front-load heading words; chunk + highlight keywords; "most users will read very little from a wall of text."
— NN/g, Pernice, *The Layer-Cake Pattern of Scanning Content on the Web* (2019-08-04), https://www.nngroup.com/articles/layer-cake-pattern-scanning/ (accessed 2026-09-22); NN/g, Pernice, *Text Scanning Patterns: Eyetracking Evidence* (2019-08-25), https://www.nngroup.com/articles/text-scanning-patterns-eyetracking/ (accessed 2026-09-22).
- **Still true in 2020:** "People still primarily scan, rather than read… Scanning all of the text on a page… is still extremely rare" — support scanning with plain language, bulleted lists/bold, front-loading, and clear headings/subheadings.
— NN/g, Moran, *How People Read Online: New and Old Findings* (2020-04-05), https://www.nngroup.com/articles/how-people-read-online/ (accessed 2026-09-22).

### 2.4 The 2026 shift: dual audience (humans + coding agents)

- **AGENTS.md is explicitly a *separate* file, not a README section:** "Think of AGENTS.md as a **README for agents**"; "README.md files are for humans: quick starts, project descriptions, and contribution guidelines. AGENTS.md complements this by containing the extra, sometimes detailed context coding agents need: build steps, tests, and conventions **that might clutter a README** or aren't relevant to human contributors"; the stated intent includes "Keep READMEs concise and focused on human contributors."
— AGENTS.md, https://agents.md/ (accessed 2026-09-22).
- **AGENTS.md format is intentionally loose:** "No… required fields. AGENTS.md is just standard Markdown. Use any headings you like"; nested files per subdirectory, "closest AGENTS.md to the edited file wins"; agents will run listed test commands before finishing; treat it as living documentation. Adoption: 60k+ public repos; stewarded by the Agentic AI Foundation under the Linux Foundation.
— AGENTS.md, same URL (accessed 2026-09-22).
- **GitHub's platform reads agent files everywhere now:** Copilot coding agent supports `AGENTS.md` (root + nested) alongside `.github/copilot-instructions.md`, `.github/instructions/**.instructions.md`, `CLAUDE.md`, `GEMINI.md` (2025-08-28); Copilot code review reads repository `AGENTS.md` automatically (2026-06-18); JetBrains support includes generating an initial `AGENTS.md` (2026-03-11).
— GitHub Changelog, *Copilot coding agent now supports AGENTS.md* (2025-08-28), https://github.blog/changelog/2025-08-28-copilot-coding-agent-now-supports-agents-md-custom-instructions/ (accessed 2026-09-22); GitHub Changelog, *Copilot code review: AGENTS.md support* (2026-06-18), https://github.blog/changelog/2026-06-18-copilot-code-review-agents-md-support-and-ui-improvements/ (accessed 2026-09-22); GitHub Changelog, *Major agentic capabilities improvements in GitHub Copilot for JetBrains IDEs* (2026-03-11), https://github.blog/changelog/2026-03-11-major-agentic-capabilities-improvements-in-github-copilot-for-jetbrains-ides/ (accessed 2026-09-22).
- **GitHub-native instruction files (first-party spec):** repo-wide `.github/copilot-instructions.md`; path-specific `.github/instructions/NAME.instructions.md` with `applyTo:` glob frontmatter (optional `excludeAgent:`); Copilot CLI's discovery table covers repo root, intermediate dirs, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`. GitHub's own "onboard this repository" prompt caps instructions: **"Instructions must be no longer than 2 pages. Instructions must not be task specific"** — goals: fewer failed builds/CI, less agent foraging via grep/find.
— GitHub Docs, *Adding repository custom instructions for GitHub Copilot*, https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions (accessed 2026-09-22); GitHub Docs, *Adding custom instructions for GitHub Copilot CLI*, https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions (accessed 2026-09-22).
- **What actually works in agent files (GitHub's analysis of 2,500+ files):** put executable commands early (`npm test`, `pytest -v`, with flags); set explicit boundaries ("Never commit secrets" was the most common constraint); name the stack precisely with versions; cover six areas — commands, testing, project structure, code style, git workflow, boundaries; grow by iteration when the agent errs.
— GitHub Blog, Nigh, *How to write a great agents.md: Lessons from over 2,500 repositories* (2025-11-19), https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/ (accessed 2026-09-22).
- **llms.txt (site-level, not repo-README-level):** `/llms.txt` = H1 name + blockquote summary + H2 "file lists" of links with brief notes; "The file itself stays small enough to fit in context. The detail lives behind the links, and is fetched only when needed"; guidance: concise language, informative link descriptions, no unexplained jargon, test by querying an agent with only the file. v2 (2024-09-03, modified 2026-08-10): thousands of sites, docs platforms generate it automatically, Chrome's Lighthouse audits for it, and OpenAI/Anthropic/Gemini publish theirs for their own docs.
— llms-txt, Howard, *The /llms.txt file, v2*, https://llmstxt.org/ (accessed 2026-09-22).
- **MCP-adjacent:** GitHub's custom agents (`.github/agents/*.md`, org- and repo-level) "can be further tailored with prompts, tool selections, and Model Context Protocol (MCP) servers" — agent-facing repo config has fanned out beyond any single file; nothing first-party says README should absorb it.
— GitHub Changelog, *Custom agents for GitHub Copilot* (2025-10-28), https://github.blog/changelog/2025-10-28-custom-agents-for-github-copilot/ (accessed 2026-09-22).
- **Coexistence model (SYNTHESIS of the above):** three layers — (1) **README.md** = human orientation: what/why/quickstart/usage/help/contributing pointers; (2) **AGENTS.md / .github/copilot-instructions.md / CLAUDE.md** = operational agent context: build/test/lint commands, structure, style, boundaries (closest file wins, user chat overrides — AGENTS.md FAQ); (3) **llms.txt + `docs/*.md`** = curated docs-site index for agents fetching documentation. Each source guards its own lane; AGENTS.md exists *so that* the README stays human.

### 2.5 Anti-patterns reviewers flag

- **Changelog in README:** release history belongs to Releases — GitHub's first-party flow is "create new releases with release notes… automatically generate your release notes" (`gh release create --generate-notes`); community canon: "Changelog… is something from pre-GitHub time… rely on the releases tab."
— GitHub Docs, *Managing releases in a repository*, https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository (accessed 2026-09-22); Yegor Tsyumentsev (2019), same URL [secondary] (accessed 2026-09-22).
- **Contribution walls in README:** `CONTRIBUTING.md` is auto-surfaced by GitHub — link shown when someone opens a PR or issue, on the repo `contribute` page, a "Contributing" tab, and the sidebar; duplicating that content in the README is redundant.
— GitHub Docs, *Setting guidelines for repository contributors*, https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors (accessed 2026-09-22).
- **Wall-of-text plans / debate transcripts:** no first-party source puts process records in a README; GitHub scopes it to "information necessary… to get started using and contributing", and Microsoft names the failure mode — "Long spans of dense text are daunting and unapproachable… Write short headings, short sentences, and short paragraphs"; NN/g quantifies it (users read ~20%, unformatted chunks → F-scan → missed content). Keep decisions written down, just not here: "If you meet with other maintainers, or make a major decision in private, document these conversations in public" (i.e. issues/discussions/vision docs).
— GitHub Docs, *About the repository README file*, same URL (accessed 2026-09-22); Microsoft Style Guide, *Scannable content*, same URL (accessed 2026-09-22); NN/g (2006/2008), same URLs (accessed 2026-09-22); GitHub, *Open Source Guide — Best Practices*, same URL (accessed 2026-09-22). [placement per these = SYNTHESIS]
- **Time-rotting prose:** Google bans time-anchored wording in docs — avoid "currently", "new", "now", "latest", "soon", "eventually"; "document the current version of a product or feature"; such words are fine in release notes but not in standing docs; value: "reduces the maintenance required to keep documentation up to date."
— Google style guide, *Timeless documentation* (updated 2024-10-15), https://developers.google.com/style/timeless-documentation (accessed 2026-09-22). Corroborated by opensource.guide's delete-or-mark-outdated rule (same URL as above).
- **Stale/duplicated facts:** version numbers and dates hardcoded in README prose rot (secondary 2026: "Cut anything that names a version number, a date, or a roadmap item"); pointer-to-source beats copy-of-source.
— Omniwebkit (2026-08-08), same URL [secondary] (accessed 2026-09-22).
- **Diátaxis mode-mixing:** reference must "describe and only describe… Instead [of instructing/explaining], link to how-to guides, explanation and introductory tutorials"; how-to guides: "action and only action — no digression, explanation, teaching… if they're important, link to them"; a README section that argues, teaches, and lists flags at once is failing all four modes at once.
— Diátaxis, *Reference*, https://diataxis.fr/reference/ (accessed 2026-09-22); Diátaxis, *How-to guides*, https://diataxis.fr/how-to-guides/ (accessed 2026-09-22).
- **Format-level flags:** skipped heading levels; `#`-styled list lookalikes; emoji-as-bullets; images of terminal output/code; alert spam; badge rows; links in headings; numbered section headings ("1. Introduction"); missing alt text; empty headings; two headings in a row — all explicitly "not recommended" by the first-party sources cited in §2.3.
— Google style guide, *Headings* / *Images*, same URLs (accessed 2026-09-22); GitHub Docs, *Basic writing…* / *5 tips… accessible*, same URLs (accessed 2026-09-22).
- **Full API dump in README:** move it — reference docs should be austere and auto-generatable ("Some reference material (such as API documentation) can be generated automatically by the software it describes"), and GitHub's scope rule already excludes it.
— Diátaxis, *Reference*, same URL (accessed 2026-09-22); GitHub Docs, *About the repository README file*, same URL (accessed 2026-09-22).

### 2.6 Migration: living-plan README → thin README + linked docs

## 3. Tension resolution

- **TOC:** not either/or. GitHub auto-Outline covers navigation on rendered view (first-party); Microsoft/GitHub-blog still prescribe an in-doc TOC *for long content*. Resolution: no manual TOC under ~1.5 screens; if kept, `##`-only, generated, and never the sole navigation (headings must carry it alone for outline/agents/screen readers).
- **Brevity vs completeness:** GitHub (.NET) lists 11 "areas" while GitHub Docs says "only necessary information." Reconciled by *presence vs depth*: every area is represented, most as one line or a link; depth lives in linked docs (both sources say to split and link).
- **Badges:** first-party says CI/status badges belong in README; community says badges are noise if they carry no viewer value. Rule: status signals that a reader can act on (build, coverage, license, version), ≤~4, one row, each linked; decoration and vanity counts out.
- **Hiding content:** `<details>` is first-party-sanctioned for non-essential technical detail — but NN/g's layer-cake rule says scanning works only when headings truthfully summarize what's under them; never fold quickstart/usage/license, and label folds descriptively.
- **Human vs agent duplication:** AGENTS.md deliberately duplicates *commands* that a human README would otherwise carry as prose; keep commands in one place (AGENTS.md), and in README keep only the one-line quickstart a newcomer copies first. Both files link each other's lane.
- **Changelog/roadmap:** .NET Foundation says "roadmap or *link*"; Google bans time-anchored prose; GitHub ships Releases/Issues for exactly this. Standing rule: link, don't embed, anything that changes on a schedule.

## 5. Checklist for reorganizing a README

Apply top-to-bottom to a long plan-style README:

1. **Cut to the five GitHub topics** — what it does, why useful, how to get started, where to get help, who maintains — plus install, one runnable usage example, license link, contributing link. Delete everything not needed to "get started using and contributing" (GitHub Docs scope rule).
2. **Rebuild the skeleton in predictable order:** `# Title` + one-liner → badges (≤4: build/status/license/version, each linked) → optional screenshot/GIF → Install → Usage (copy-pasteable, output shown) → Configuration (table: name/type/default/description) → Contributing (link) → License (link). Sentence-case `##` headings, no skipped levels, one `#`.
3. **Front-load per F-pattern/layer-cake:** first paragraph states what it is; headings are descriptive, information-bearing, and accurate for their section; lead bullets with the keyword; cap bold/italic highlighting ~10% of text.
4. **Evict by Diátaxis bin:** plan steps → `docs/` how-tos or issues; decision/debate history → ADRs or issues; config/flag reference → `docs/reference` (or auto-generated API docs); rationale → explanation doc; roadmap → Issues/projects; changelog → Releases; contribution process → `CONTRIBUTING.md`; CoC/license/security → their own community-health files (GitHub auto-surfaces all of them).
5. **Move agent operational content out:** build/test/lint commands, project structure, code style, git workflow, boundaries → `AGENTS.md` (root + nested per subdir) or `.github/copilot-instructions.md`; keep it ≤2 pages, command-first, non-task-specific; link it from README's docs list.
6. **Kill rot:** delete dates, "currently/new/latest/soon", hardcoded version numbers in prose, stale screenshots, dead badges; mark or remove anything you won't update (Google timeless + opensource.guide).
7. **Fix images:** keep 1–3 cropped screenshots (one OS, no PII), never screenshots of code/terminal output — paste that as fenced code blocks; write tweet-length alt text on every image; relative image paths inside the repo.
8. **Chunk for scanning:** paragraphs 3–7 lines; lists ≤7 parallel items; tables only for matrix data (flags, options, env vars); fold genuinely optional detail in `<details>` with a descriptive `<summary>` — never fold the quickstart, usage, or license.
9. **Ration callouts:** 1–2 alerts (`> [!NOTE]` etc.) per README, never consecutive; no emoji-as-bullets; real list markup only; descriptive link text (no "click here").
10. **Navigation:** rely on GitHub's auto-Outline; only add a manual TOC if the file is still very long after the split (`##` depth only, keep it 3 lines or fewer of churn); use relative links, single-line link text, and preserve heading text so anchors stay stable — update inbound links if you rename headings.
11. **Two-paragraph test:** a stranger answers "what is this / how do I run it" within the first screen and ≤2 paragraphs; if not, rewrite the top, don't add more sections.
12. **Length budget:** target ≤1 screen of scrolling for the core (title → runnable example) and well under a few hundred lines total; anything past that must be a link (secondary 2026 norm: ~100–300 lines; hard ceiling 500 KiB truncation).
13. **Link the lanes both ways:** README → `docs/`, `AGENTS.md`, CONTRIBUTING, Releases, Issues/roadmap; `AGENTS.md` → README for human context; docs `llms.txt` (if a docs site exists) → markdown pages, with the index kept small.
14. **Verify on GitHub's rendered view:** Outline shows a sane `##` spine; no broken relative links; badges load and link; alerts ≤2; heading levels contiguous; run `markdownlint` (GitHub's a11y post ships an Actions snippet) before merging the rewrite.
